# SubScope

**你同意订阅的那份账单，和你真在付的那份账单。**

自动续费被设计得让人忽略：一个月十五块，静默续期，悄悄涨价，开头还是一分钱的试用。
没人取消，因为没人算总账。SubScope 读一份账单文件，把每一笔周期性扣款按**一年多少钱**
报出来——而不是一个月多少钱——然后标出那些**变过**的。

## 运行

```bash
python eval.py     # 80 条断言，离线，仅依赖标准库
python demo.py     # 一年的普通消费，以及没人注意到的那些
```

零联网、零 API Key、零第三方包。

## 能查出什么

| 信号 | 含义 | 怎么算出来的 |
|---|---|---|
| **周期性扣款** | 这是订阅，不是单次购买 | 同一商户 ≥3 笔，且间隔**中位数**落在周期带内 |
| **年化成本** | 它到底花你多少钱 | 最近一次价格 × 12 / 52 / 4 / 1（按周期） |
| **涨价** | 它涨了而你没注意 | 金额序列不平坦；报出次数与累计涨幅 |
| **试用转付费** | 一分钱的试用变成了订阅 | 首笔 ≤ ¥1.00 而当前不是 |
| **小额失血** | 单次便宜，一年很贵 | 单次 ≤ ¥15 但年化 ≥ ¥100 |
| **沉默时长** | 它悄悄续了多久 | 首末笔之间的月数 |
| **重复扣款** | 同一笔收了两次 | 同商户、同金额、24 小时内 |

## 设计契约

* **仅标准库** —— Python 能跑的地方它就能跑
* **检测路径上没有模型** —— 「你每个月都被扣钱」是算术，不是推断。引入模型只会让它变成概率性的，而且更糟
* **整数分** —— 钱从不接触浮点
* **确定性** —— 同一份账单文件产出逐字节相同的输出；这里没有任何一处读系统时钟
* **不上云** —— 账单文件在本地解析。一个读遍你所有消费记录的工具，不该把它传出去

## 为什么用中位数而不是均值

漏扣一个月会产生一个约 60 天的间隔。把它平均进月度订阅，周期会被拽向季度区间，
这笔订阅就从报告里**彻底消失**——这是最糟的一种失败，因为输出看起来仍然合理。
中位数会忽略它。这一点有断言覆盖：`[30, 31, 28, 90]` 必须仍判为月度。

## 归一化

支付宝、微信和通用银行导出在列名、日期格式、正负号约定、什么算一笔消费上各不相同。
每个来源一个适配器，统一成同一种记录结构，检测逻辑因此永远不需要知道账单来自哪里。

有两个比看上去更重要的细节：

* **中性行被丢弃**。支付宝导出里有「不计收支」——退款和内部转账。把它们当成消费，
  会凭空造出从未离开账户的扣款。
* **商户名统一大写并压缩空白**，同一个收款方才会被归成一组。

